Apache Airflow
Workflow Orchestration
Must Know Growing
Industry Adoption
79%
Demand Score
9.5 / 10
Difficulty
Intermediate
Salary Impact
+15–20%
Python-based platform for authoring, scheduling, and monitoring data pipelines as DAGs (Directed Acyclic Graphs). De-facto standard for orchestration in 4–6 yr DE roles.
Problem Solved
Dependency management between pipeline tasks, retry logic, backfilling historical data, SLA monitoring, and centralised scheduling with visibility into pipeline runs.
Architecture Fit
Sits at the orchestration layer. Triggers ETL jobs (Glue, Spark, dbt), calls APIs, monitors data quality checks. Often runs on Kubernetes (KubernetesPodOperator) or as MWAA/Cloud Composer.
Prerequisites
Python, SQL, basic understanding of ETL concepts, Linux/Bash.
Alternatives
Dagster (modern, asset-oriented), Prefect (Python-native), Luigi (simpler), Databricks Workflows (within Databricks), Azure Data Factory (Azure-native).
🎯 Most Asked Interview Questions
  • What is a DAG? How do you handle task dependencies and dynamic DAGs?
  • Explain XComs — what are their limitations for large data passing?
  • How do you implement backfilling? What are catchup and max_active_runs?
  • Difference between BranchPythonOperator and ShortCircuitOperator?
  • How do you deploy Airflow on Kubernetes? What is KubernetesPodOperator?
  • How do you handle secrets/connections securely in Airflow?

  • Explain partitioning strategies — repartition vs coalesce?
  • How do you debug and optimize slow Spark jobs? (Spark UI, stage analysis)
  • What is the difference between persist() and cache()?

Data Engineering Architecture Patterns
Comprehensive visual diagrams for every major architecture. These are the most asked design questions in senior DE interviews.
🥉🥈🥇 Medallion Architecture (Bronze / Silver / Gold)
Most commonly asked architecture in 2024–2025 interviews. Databricks & Delta Lake native.
graph LR A[📡 Sources\nDBs · APIs · Files · Streams] -->|Raw Ingest| B[🥉 BRONZE\nRaw Layer] B -->|Cleanse & Type| C[🥈 SILVER\nConformed Layer] C -->|Business Logic| D[🥇 GOLD\nCurated Layer] D -->|Serve| E[BI / ML / Apps] style B fill:#8B4513,color:#fff,stroke:#8B4513 style C fill:#708090,color:#fff,stroke:#708090 style D fill:#DAA520,color:#000,stroke:#DAA520
Bronze: Raw, unprocessed data. Schema-on-read. Append-only. Keeps original format. No quality checks.
Silver: Cleansed, typed, deduplicated. Schema enforcement. Basic quality checks applied. Joined from multiple bronze tables.
Gold: Business-aggregated, domain-specific, denormalized for consumption. Fact/dimension tables, KPI tables. Consumed by BI tools and ML.
⚡ Lambda Architecture
Batch + Speed + Serving layers for low-latency + historical accuracy.
graph TD A[📡 Data Source] --> B[Ingestion Layer\nKafka / Kinesis] B --> C[🗄 Batch Layer\nSpark / HDFS\nHigh latency, complete accuracy] B --> D[⚡ Speed Layer\nSpark Streaming / Flink\nLow latency, approximate] C --> E[Serving Layer\nHBase / Cassandra] D --> E E --> F[BI / Applications] style C fill:#1a2a4a,color:#38bdf8 style D fill:#2a1a1a,color:#fb923c style E fill:#1a2a1a,color:#34d399
Limitation: Maintaining two separate codebases (batch + speed) is operationally complex. The reason Kappa Architecture was proposed.
κ Kappa Architecture
Single streaming pipeline replaces batch + speed layers. Simpler operations.
graph LR A[📡 Sources] -->|All data as events| B[Kafka / Kinesis\nImmutable log] B -->|Real-time processing| C[Flink / Spark Streaming] C -->|Write results| D[Delta Lake / Iceberg] D --> E[Serving\nBigQuery / Snowflake] E --> F[BI / ML] style B fill:#1a1a3a,color:#a78bfa style C fill:#1a3a1a,color:#00ffc8
Reprocessing done by replaying Kafka from earliest offset. One codebase. Works well when Kafka retention is long enough.

Combines data lake flexibility with data warehouse performance. Open standard.

🔄 Change Data Capture (CDC) Architecture
Replicate database changes in real-time using transaction log parsing.
graph LR A[(Source DB\nPostgres · MySQL\nOracle · SQL Server)] -->|Binary Log| B[Debezium\nConnector] B -->|Change Events| C[Kafka\nTopic per table] C -->|Consume| D[Spark Streaming\nor Flink] D -->|MERGE INTO| E[Delta Lake\nor Snowflake] E -->|Serve| F[BI / dbt] style B fill:#2a1a2a,color:#f472b6 style C fill:#1a1a2a,color:#a78bfa style D fill:#1a3a1a,color:#00ffc8
Event types: INSERT (after image), UPDATE (before+after), DELETE (before image with tombstone). Initial snapshot + ongoing CDC for first load.

⚡ Photon Engine — Vectorized C++ Query Engine ▼

What it is: Photon is a native vectorized execution engine written in C++ that replaces the JVM-based Spark engine for SQL and DataFrame operations. It's available on Databricks runtime clusters and SQL warehouses.

Performance: 2x–4x faster on scan-heavy workloads, aggregations, joins, and SQL ANSI operations. Works automatically — no code changes needed.

When it helps most: Wide table scans, large aggregations, hash joins, string operations. Less helpful for: heavy UDF usage (Python UDFs run outside Photon), complex ML pipelines.

Interview question: "When would you NOT expect Photon to improve performance?" → Python UDFs, operations not yet Photon-supported, I/O bound pipelines.

🔄 Auto Loader — Incremental Cloud File Ingestion ▼

What it is: Databricks Auto Loader (cloudFiles source) incrementally ingests new files from cloud storage (S3, ADLS, GCS) as they arrive. Uses file notification or directory listing mode.

Key features: Schema inference and evolution, checkpointing (exactly-once), rescue data column, file notification (SQS/Event Grid) vs directory listing mode, supports JSON, CSV, Parquet, ORC, Avro, text.

Interview question: "Explain the difference between directory listing and file notification in Auto Loader — when do you choose each?"

df = spark.readStream\
    .format("cloudFiles")\
    .option("cloudFiles.format", "json")\

    .load(input_path)
📊 Delta Live Tables — Declarative Pipeline Framework ▼

What it is: DLT lets you define data pipelines using Python or SQL decorators. Databricks handles execution, error recovery, data quality enforcement, and lineage automatically.

Key concepts: @dlt.table (batch), @dlt.view, Streaming Live Tables (for Auto Loader), APPLY CHANGES INTO (CDC upserts), Expectations (quality constraints with warn/fail/quarantine).

Modes: Development mode (immediate feedback, no restarts), Production mode (continuous or triggered execution).

@dlt.expect_or_drop("valid_order", "order_id IS NOT NULL")

    return dlt.read("bronze_orders")\
        .dropDuplicates(["order_id"])
🔗 Unity Catalog — Unified Governance & Lineage ▼

3-level namespace: catalog.schema.table (e.g., prod_catalog.sales.orders). Single governance layer across all Databricks workspaces and clouds.

Key features: Fine-grained access control (column/row-level masking), data lineage (automatic at table and column level), audit logs, data discovery, external table registration, Delta Sharing.

Open Table Format
26% JDs

SQL on Hadoop (Legacy)
29% JDs

Apache Parquet
Columnar File Format
65% JDs
Columnar binary file format optimized for analytics. Row groups (128MB), column chunks, page encoding (dict, RLE, bit-packing). Compression codecs: Snappy (default), Zstd, Gzip, LZ4. Critical for query pushdown.
Parquet vs Avro vs ORC
Parquet: analytics/columnar read — best for SELECT. Avro: row-based, schema evolution, streaming/Kafka. ORC: Hive-native columnar, slightly better compression. JSON: human-readable, worst performance.
Apache Hadoop
Distributed Storage (Legacy)
35% JDs
HDFS + YARN + MapReduce ecosystem. Being replaced by cloud object stores (S3/ADLS/GCS) + Spark. Still relevant in on-prem and legacy banking/telecom environments. Knowledge of HDFS architecture useful for interview context.
Apache Druid
Real-Time OLAP DB
8% JDs
Sub-second OLAP queries on streaming and batch data. Pre-aggregation (rollup), bitmap indexing. Used for high-concurrency dashboards at Lyft, Twitter, Airbnb. Datasources ingest from Kafka/S3.

Window Functions
-- ROW_NUMBER: unique rank per partition
SELECT *, ROW_NUMBER() OVER (
  PARTITION BY dept ORDER BY salary DESC
) AS rn FROM employees;

-- LAG / LEAD: compare rows
SELECT date, revenue,
  LAG(revenue,1) OVER (ORDER BY date) AS prev,
  revenue - LAG(revenue,1) OVER (ORDER BY date) AS delta
FROM sales;

-- DENSE_RANK vs RANK
-- RANK: gaps after ties | DENSE_RANK: no gaps
SELECT name, score,
  RANK()       OVER (ORDER BY score DESC) AS rank,
  DENSE_RANK() OVER (ORDER BY score DESC) AS drank
FROM results;
CTEs & Recursive
-- Standard CTE
WITH monthly_rev AS (
  SELECT DATE_TRUNC('month', dt) AS mo,
         SUM(amount) AS total
  FROM orders GROUP BY 1
)
SELECT mo, total,
  SUM(total) OVER (ORDER BY mo) AS running
FROM monthly_rev;

-- Recursive CTE (org hierarchy)
WITH RECURSIVE org AS (
  SELECT id, name, parent_id, 1 AS lvl
  FROM employees WHERE parent_id IS NULL
  UNION ALL
  SELECT e.id, e.name, e.parent_id, o.lvl+1
  FROM employees e
  JOIN org o ON e.parent_id = o.id
)
SELECT * FROM org ORDER BY lvl;
SCD Type 2 with MERGE
-- SCD2: Expire old + Insert new
MERGE INTO dim_customer AS t
USING staging_customer AS s
  ON t.customer_id = s.customer_id
     AND t.is_current = TRUE
WHEN MATCHED AND (
  t.name != s.name OR t.email != s.email
) THEN UPDATE SET
  t.is_current = FALSE,
  t.end_date = CURRENT_DATE
WHEN NOT MATCHED THEN INSERT (
  customer_id, name, email,
  start_date, end_date, is_current
) VALUES (
  s.customer_id, s.name, s.email,
  CURRENT_DATE, NULL, TRUE
);

from confluent_kafka import Producer
import json

conf = {
    'bootstrap.servers': 'broker:9092',
    'acks': 'all',         # strongest durability
    'retries': 3,
    'linger.ms': 5,        # batch for 5ms
    'compression.type': 'snappy'
}
producer = Producer(conf)

def delivery_report(err, msg):
    if err:
        print(f'Delivery failed: {err}')
    else:
        print(f'Delivered to '
              f'{msg.topic()}[{msg.partition()}]'
              f' @ {msg.offset()}')

# Produce with key (ensures ordering)
event = {"order_id": "ORD-001", "amount": 99.50}
producer.produce(
    topic='orders',
    key='customer-123',
    value=json.dumps(event).encode('utf-8'),
    callback=delivery_report
)
producer.flush()
Consumer + Exactly-Once
from confluent_kafka import Consumer

conf = {
    'bootstrap.servers': 'broker:9092',
    'group.id': 'orders-processor-v1',
    'auto.offset.reset': 'earliest',
    'enable.auto.commit': False  # manual commit!
}
consumer = Consumer(conf)
consumer.subscribe(['orders'])

try:
    while True:
        msg = consumer.poll(timeout=1.0)
        if msg is None: continue
        if msg.error(): handle_error(msg.error())

        # Process message
        process(msg.value().decode('utf-8'))

        # Commit AFTER successful processing
        consumer.commit(asynchronous=False)
finally:
    consumer.close()

# Delivery semantics:
# at-most-once:  auto-commit before process
# at-least-once: commit after process (default)
# exactly-once:  Kafka transactions + idempotent
Key Concepts Reference
Partition — unit of parallelism; messages with same key → same partition
Offset — position of message in partition (immutable)
Consumer Group — each partition assigned to one consumer in group
Replication Factor — RF=3 means 3 copies across brokers
ISR — In-Sync Replicas; acks=all waits for all ISR to confirm
Log Compaction — retain only latest value per key (for CDC)

  URL = 's3://my-bucket/landing/'
  CREDENTIALS = (AWS_ROLE='arn:aws:iam::...')
  FILE_FORMAT = (TYPE=PARQUET);

-- Snowpipe (continuous ingest)
CREATE PIPE orders_pipe
  AUTO_INGEST = TRUE
AS
COPY INTO raw.orders
FROM @orders_stage
FILE_FORMAT = (TYPE=PARQUET);

-- Time Travel (up to 90 days Enterprise)
SELECT * FROM orders AT (
  TIMESTAMP => '2025-01-01 00:00:00'::TIMESTAMP
);
-- or offset in seconds:
SELECT * FROM orders AT (OFFSET => -3600);
Streams & Tasks (CDC)
-- Stream captures inserts/updates/deletes
CREATE STREAM orders_stream
  ON TABLE raw.orders
  APPEND_ONLY = FALSE;  -- track all DML

-- Task to process stream on schedule
CREATE TASK process_orders
  WAREHOUSE = transform_wh
  SCHEDULE = 'USING CRON 0 * * * * UTC'
WHEN
  SYSTEM$STREAM_HAS_DATA('orders_stream')
AS
MERGE INTO silver.orders AS t
USING (
  SELECT * FROM orders_stream
  WHERE METADATA$ACTION = 'INSERT'
) AS s ON t.order_id = s.order_id
WHEN MATCHED THEN UPDATE SET ...
WHEN NOT MATCHED THEN INSERT ...;

ALTER TASK process_orders RESUME;

Section 14
Hidden Skills
Companies rarely list these explicitly but test heavily — or assume them on Day 1 at senior level. These are the silent filters in every technical interview.
⚡ Pipeline Idempotency

Understanding that pipelines must produce the same result regardless of how many times they run. Companies assume this for any mid-level+ candidate but almost never write it in JDs. Tested through system design questions.

⏰ Late-Arriving Data Handling

Designing for out-of-order events in batch and streaming. Watermark configuration in Spark Streaming, reprocessing logic, and backfill strategies are universally expected but rarely stated explicitly in JDs.

💰 Cost Awareness / FinOps

Writing BigQuery queries that reduce slot usage, right-sizing Snowflake warehouses, using Spot/Preemptible instances for Spark clusters. Cost-conscious engineering is a silent hiring filter at senior level.

📊 Monitoring & Alerting

Setting up DAG failure alerts, row-count anomaly detection, SLA tracking. JDs say "ensure reliability" but never specify CloudWatch / Grafana / PagerDuty integration skills that this actually requires.

🔍 Data Lineage Understanding

Tracing data from source to consumption — column-level lineage in dbt, Spark event logs, catalog lineage. Companies building for compliance expect this as standard but list it as "familiarity with governance."

🔄 Schema Evolution Handling

Backward/forward compatibility in Avro schema registry, MERGE on Delta Lake with schema drift, graceful handling of new upstream columns without breaking downstream consumers.

🗣 Stakeholder Data Literacy

Translating business questions into pipeline requirements and pipeline errors into business impact. Listed as "communication skills" in JDs but is actually a deep technical-to-business translation capability.

🌿 Git Workflow for Data

Feature branches for dbt models, PR-based SQL review, semantic versioning for data models, tagging releases. Assumed at senior level but tested indirectly through portfolio and GitHub profile review.

🚨 On-Call / Incident Response

Debugging a failed pipeline at 2 AM, interpreting Spark UI, reading GC logs, triaging Kafka consumer lag. "Strong problem solving" in JDs means this. Never stated, always required at senior level.

📝 Naming & Documentation Culture

Consistent table/column naming, dbt docs-generate discipline, README culture. Accenture/TCS specifically test for this in code-submission rounds but never mention it in JDs. Separates professionals from coders.

🔐 Security & PII Handling

Dynamic data masking in Snowflake, column-level security in BigQuery, tokenization patterns for PII, IAM least-privilege design. Listed as "data governance" in JDs but assumed as hands-on experience.

📐 Dimensional Modeling Depth

Not just star schema — when to denormalize, when to use wide tables for analytics, OLAP vs OLTP trade-offs, bridge tables for many-to-many. Tested in almost every system design round for senior roles.
